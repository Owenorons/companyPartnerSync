## 1. Purpose

Capture every concrete gap, bug, orphaned feature, and piece of dead configuration found by a full-project audit (grep-verified against actual code, not assumption), prioritized by real-world impact, so work can be picked off in order without re-deriving the inventory each time.

## 2. Method

Verified by reading code directly (2026-09-25): existence checks for every phase in `prm-gap-remediation-build-plan.md`, a full site-wide navigation reachability sweep (every `sfdc_cms__route` cross-checked against `navigationMenu-meta.xml` files, dashboard quick-action tiles, and every `NavigationMixin`/`comm__namedPage` call in `force-app/main/default/lwc`), an Apex/LWC test-coverage sweep, a permission-set FLS completeness check for recently-added schema, and a sweep of every `__mdt` custom metadata type for live Apex consumers.

**4.4 — `Deal_Review__c` checklist engine, now wired (2026-09-25).** Was unwired with the same assignment flaw Phase 8a fixed for approvals: `DealReviewPlanService.generate()` had zero production callers, and its two seeded rules (`Commercial_Review`, `Channel_Review`) used `Assignment_Type__c = 'Current User'` — which, if wired naively into submission, would have assigned every review to the _submitting partner_ rather than an internal reviewer.

**What shipped:** ported the exact `'Permission Set'` assignment fix Phase 8a proved out for `Approval_Step_Rule__mdt` — `Deal_Review_Routing_Rule__mdt.Assignment_Type__c` (Text → restricted Picklist: `Permission Set` default, `Current User`) + new `Approver_Permission_Set__c`, new `Deal_Review__c.Approver_Permission_Set__c` snapshot field, `DealReviewPlanService.generate()` updated to resolve it. Re-pointed the seeded rules: `Channel_Review` → `PartnerSync_Channel_Manager`, `Commercial_Review` → `PartnerSync_Deal_Reviewer`. Wired `DealReviewPlanService.generate()` into `RegistrationLifecycleCommandHandler.routeSubmission()` alongside the approval plan.

Also found and fixed a second, deeper gap while building this: `DealReviewCommandService.execute()` (Start/Complete/Request Info/Resume/Reassign/Recuse/Waive/Escalate/Cancel) had **zero callers anywhere** — not just `generate()`, the entire per-step action engine was unreachable, with no authority check of its own. Built the missing layer: `DealReviewStepSelector`/`DealReviewStepDomain`/`DealReviewStepWorkspaceService`/`DealReviewStepController` (mirroring the `Approval*` workspace family) + new `psDealReviewStepWorkspace` LWC, added to the `Deal_Review` Experience Cloud page. Added `DealReviewCommandService.assertAuthority()` (routed assignee/permission-set match), with `Reassign` gated by general review-management authority (`PartnerPermissionService.canReviewDeals()`) instead, specifically so a `Routing Failed` step — which nobody is routed to by definition — still has a recovery path.

**Real production behavior change, not just a UI fix:** `RegistrationLifecycleCommandHandler.assertNoBlockingReviews()` already existed and was already wired into `FINALISE_APPROVAL`, but was vacuously always-passing since no `Deal_Review__c` ever existed. It's real enforcement now — every deal submission generates its review checklist (Channel_Review always; Commercial_Review too above $50k), and blocking items must be completed before final approval, not just the approval chain. This was already the intent baked into the seed data (`Blocking__c = true` on both rules pre-dates this fix); wiring `generate()` in makes it actually happen. Required fixing `RegistrationLifecycleCommandHandlerTest.cls`'s one test that reaches `FINALISE_APPROVAL` after a real `SUBMIT`, to also complete the Channel_Review step first.

Evidence: `force-app/main/default/classes/deals/DealReviewPlanService.cls`, `DealReviewCommandService.cls`, `DealReviewStep*.cls`, `force-app/main/default/lwc/psDealReviewStepWorkspace/`. **Status: done.**

**Known follow-up, not fixed here:** `PartnerPermissionService.canReviewDeals()`'s backing list (`DEAL_REVIEW_PERMISSION_SETS`) only recognizes `PartnerSync_Channel_Manager`/`PartnerSync_Internal_Admin`, not `PartnerSync_Deal_Reviewer` — despite that permission set existing specifically for deal review and already holding `DealReviewController`/`ApprovalController` class access. A `PartnerSync_Deal_Reviewer`-only user can work their own Commercial_Review steps fine (gated by direct permission-set membership via `assertAuthority()`), but can't `Reassign` any review, including their own, since Reassign needs `canReviewDeals()` specifically. Worth deciding whether to add `PartnerSync_Deal_Reviewer` to that list in a follow-up pass.

The live gap is 1.3, not a missing caller.
