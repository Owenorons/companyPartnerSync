# AI Governance & Portfolio Intelligence — Sprint 43

## 1. What shipped (2026-09-28)

All 7 phases of the approved plan (`architecture-design-and-enhancement.md` §43, lines ~19158-21453, "PartnerSync AI, Agentforce & Portfolio Intelligence Architecture") were built in this pass, scoped deliberately to the deterministic governance/audit/aggregation substance the doc's own 24-item Definition of Done is mostly made of — real Agentforce/Einstein configuration is out of scope (§3 below), matching this project's consistent treatment of AI/Agentforce across every prior sprint.

1. **Schema** — 5 new objects (`AI_Interaction__c` the full audit trail, `AI_Recommendation__c`, `AI_Evidence__c`, `AI_Feedback__c`, `Partner_Portfolio_Snapshot__c`), plus a small 6th, `AI_Use_Case_Usage_Day__c`, added mid-build once the existing `AI_Usage_Day__c`'s `Day_Key__c` uniqueness turned out to make it unsuitable for a second, per-use-case quota counter (see §2). 4 new CMDTs (`AI_Context_Policy__mdt`, `AI_Action_Policy__mdt`, `AI_Grounding_Source__mdt`, `AI_Usage_Policy__mdt`) — additive only; `AI_Feature_Config__mdt`/`AI_Provider_Config__mdt` are reused unchanged, per the doc's own instruction not to build a competing framework.
2. **Context & Grounding** — `IntelligenceContextService.buildContext()` (an `AI_Context_Policy__mdt` field allowlist, never a raw `SELECT *`, fails closed to an empty context when no policy is configured) and `GroundingService.findEvidence()` (bounded SOQL relevance lookup, no embeddings/vector search). Both support a fixed set of objects via an explicit branch rather than dynamic SOQL, matching this codebase's established static-SOQL convention (the same tradeoff `PartnerShareService` already accepts for target objects).
3. **Interaction & Audit** — `AIInteractionService.execute()` is the single synchronous entry point: resolves context + evidence, checks both the tenant-wide (`AIUsageService.reserve()`) and new per-use-case (`AIUsageService.reserveForUseCase()`) daily quotas, calls the existing `AIProviderRouter`/`AIProvider` abstraction completely unchanged, and persists a full `AI_Interaction__c` row (plus `AI_Evidence__c` rows) for every outcome — success, policy-block, quota-block, or provider failure alike. `AIFeedbackService` is a thin feedback insert.
4. **Agent Action Gateway** — `AgentActionGatewayService.proposeAction()`/`.executeAction()`: a deterministic authorization + Command Bus dispatch layer, gated by `AI_Action_Policy__mdt`. Authority is re-checked at execute time, never trusted from propose time. This is the real entry point a future Agentforce Action would call once one exists in this org (§3, Known Adaptation #1) — fully built and tested today, independent of that.
5. **Portfolio Intelligence** — `PartnerPortfolioSnapshotBatch`: a genuine bulk design from day one, computing one `Partner_Portfolio_Snapshot__c` per active partner per run using ~11 aggregate SOQL calls total (regardless of chunk size), mirroring `AnalyticsSelector.selectKpiTotals()`'s own "N queries regardless of partner count" shape. The health score is never reimplemented — it's computed via the exact same pure `AnalyticsDomain.calculatePartnerKPI()`/`PartnerHealthScoringService.calculate()` path the existing partner KPI/leaderboard feature already uses. `PortfolioNarrativeService.generateNarrative()` is an optional, explicit, internally-triggered AI summary of a snapshot's own already-computed numbers only — never raw partner records.
6. **Sharing, permissions, events, UI** — 2 new custom permissions (`PartnerSync_View_Portfolio_Intelligence` internal, `PartnerSync_Submit_AI_Feedback` partner-facing), both with real Apex consumers checked before this phase closed. Object CRUD for the 5 new objects on `PartnerSync_Channel_Manager` (full) and a narrow read/create slice on `PartnerSync_Partner_User` for their own `AI_Recommendation__c`/`AI_Feedback__c` rows. 5 new event types across both event-consumer maps. `PortfolioIntelligenceController` (thin pass-through, mirrors `CustomerSuccessController`'s shape) and `psPortfolioIntelligencePanel` (internal, on `psInternalDashboard` via the established tracked `<property>` pattern).
7. **Bulk & concurrency hardening** — see §2; two real gaps were found and fixed during this build, plus the applicable concurrency pairs were proven with the same-test-method two-step technique used throughout this codebase.

**Verification**: every phase was checked for Apex brace/paren balance and XML well-formedness; `prettier --check`, `eslint`, and a full `sfdx-lwc-jest` run were clean at the end, at **65/65 suites, 239/239 tests** (up from 64/236 at the start of this build). No `sf deploy`/`sf validate` — user pushes to the org manually.

## 2. Real gaps found and fixed along the way (not in the original plan)

- **`AI_Usage_Day__c.Day_Key__c` is already unique per day, tenant-wide** — the original plan's "layer a per-use-case quota on top of `AIUsageService`'s existing daily quota" did not initially account for the fact that `Day_Key__c` alone being unique means a second row for the same day (for a per-use-case counter) would violate that constraint. Caught before writing any org-facing code by reading `AI_Usage_Day__c`'s actual field metadata; fixed by adding a genuinely separate `AI_Use_Case_Usage_Day__c` object keyed by `Use_Case_Key__c + '|' + day`, rather than guessing the existing object's schema would tolerate a second counter shape.
- **`OpenAIProvider.generate()` re-resolves `AI_Provider_Config__mdt.getInstance('OpenAI')` internally**, independent of `AIProviderRouter.providerConfigForTest` (which only affects routing, not the provider's own config lookup). This was verified directly against the real shipped `AI_Provider_Config.OpenAI` record (which does have `Named_Credential__c = 'PartnerSync_OpenAI'` populated, just `Active__c = false`) before writing `AIInteractionServiceTest`'s success-path test, avoiding a test that would have silently never reached a real success path.
- **The initial plan text assumed `AIUsageService.reserve()`'s thrown exception always meant "quota exceeded,"** but it also throws for a missing `PartnerSync_Generate_AI_Insights` permission (it asserts that internally). `AIInteractionService.execute()` was corrected to check `PartnerPermissionService.canGenerateAIInsights()` explicitly and separately, before calling `reserve()`, so a permission failure is correctly audited as `Blocked-Policy` rather than mislabeled `Blocked-Quota`.
- **`Deal_Registration__c`/`Customer_Commercial_Entitlement__c` have no dollar-amount field usable for a naive "renewal value at risk" rollup** — `Partner_Renewal__c` itself carries no currency field. Resolved by traversing `Current_Deal__r.Approved_Revenue__c` in the aggregate SOQL instead of fabricating a number or adding a redundant duplicate currency field to `Partner_Renewal__c`.

## 3. Known Adaptations (deliberate, labeled, not silently dropped)

1. **No real Agentforce configuration** (agents/topics/actions in Setup/Agent Builder) — declarative org config, not buildable as `force-app` source. `AgentActionGatewayService` is the standalone, fully-tested Apex entry point a real Agentforce Action would call once one is configured; wiring that Action is a manual post-deploy step for the user, the same category as the pending beta package version.
2. **No real Salesforce/Einstein AI provider** — `AIProvider` ships `OpenAIProvider`/`AzureOpenAIProvider`/`DisabledAIProvider`; no new provider implementation was added. Every new use case's shipped `AI_Feature_Config__mdt` record follows the existing `LeadFitScoring` precedent exactly (`Enabled__c = true`, `Provider_Name__c = 'OpenAI'`) and stays safe by default only because the org's real `AI_Provider_Config.OpenAI` record ships `Active__c = false` until an admin activates it — the same layered fail-safe every existing AI feature in this org already relies on.
3. **No live retrieval/vector infrastructure** — `GroundingService` is bounded SOQL relevance lookup only.
4. **Commercial AI entitlement/billing wiring is out of scope** — per the doc's own later correction placing this in a later "Wave 6."
5. **`psAiGovernanceConsole` still has no page** — a pre-existing gap (confirmed unchanged again this sprint), not something this sprint's own new code needed to unblock; left for a future UI pass.
6. **Only one copilot UI was built** (`psPortfolioIntelligencePanel`) rather than the doc's five separate copilots — all five would consume the exact same context/interaction/recommendation services this sprint built; one real, end-to-end panel proves the plumbing without four more near-duplicate panels adding no further architectural value.
7. **`Deal_Portfolio_Snapshot__c` was not built separately from `Partner_Portfolio_Snapshot__c`** — a deal already has its own live status/health/stage fields; only the cross-deal, cross-partner rollup was genuinely new.

## 4. What a future phase would need to complete

- A real Salesforce/Einstein `AIProvider` implementation, or activating the existing `OpenAI`/`AzureOpenAI` provider configs with real credentials, once the org is ready to spend on live AI calls (Adaptation #2).
- `psAiGovernanceConsole` finally getting a real page/tab (Adaptation #5) — unrelated to this sprint's own scope, but increasingly overdue.
- The remaining four copilots (Channel Manager/Deal Review/Partner/Customer Success-specific, beyond the one Portfolio Intelligence panel built here), if ever justified by real usage of the one that exists (Adaptation #6).
- Additional `AI_Context_Policy__mdt`/`AI_Grounding_Source__mdt`/`AI_Action_Policy__mdt` rows for more use cases beyond the two real ones this sprint wired end-to-end (`PortfolioNarrative`, `RenewalRiskAdvisor`) — the governance layer is generic and ready for more, each new use case just needs its own policy rows and (for actions) a compiled dispatch branch in `AgentActionGatewayService`.
