# Lead Management & Deal Conflict — Phase 1 Toward the PDLM Target Architecture

**Status: design/planning for Phase 1, with schema hygiene already shipped.** [docs/architecture-design-and-enhancement.md](architecture-design-and-enhancement.md) is the authoritative target architecture (confirmed with the owner 2026-09-25) — specifically **Sprint 22B** (Partner Lead Distribution & Assignment Lifecycle v2) and **Sprint 35** (Validation and Conflict Engine v2). This document supersedes an earlier draft of itself that proposed a smaller, independently-invented design (Round Robin CMDT wiring, `Datacloud.FindDuplicates` as the primary conflict mechanism) written before that master doc had been read in full. This version instead scopes a **first phase** of Sprint 22B and Sprint 35 — not the full sprints, which are large multi-object, multi-service designs — following those sprints' own field/object/command specs, trimmed to what's achievable as one focused delivery.

## 1. Purpose

Reconcile "what Sprint 22B/35 specify" against "what's actually live," so Phase 1 adds exactly the missing pieces rather than rebuilding things that already exist under different names, and so the scope is honest about what's deferred.

## 2. The surprise: both areas are further along than the first-pass review found

A closer read of the live schema (2026-09-25) shows PartnerSync has already implemented large parts of Sprint 35's `Deal_Conflict__c` field model and command layer — just not the read/UI layer that would make it usable, and not yet generalized past one rule.

### 2.1 Conflict engine (Sprint 35) — the command layer is built and permissioned, but has no UI

- `Deal_Conflict__c` already carries most of Sprint 35 §35.6's field model **inline** (not split into sub-objects the way the spec proposes, but functionally present): classification (`Type__c`, `Subtype__c`, `Severity__c`, `Confidence__c`, `Match_Score__c`, `Blocking__c`), investigation (`Status__c`, `Assigned_To__c`, `Investigation_Started_On__c`, `Escalated_On__c`), evidence (`Evidence_JSON__c`, `Evidence_Summary__c`, `Evidence_Requested_On__c`, `Evidence_Submitted_On__c`, `Reviewed_Evidence__c`), waiver governance (`Waived_By__c`, `Waived_On__c`, `Waiver_Reason__c`, `Waiver_Conditions__c`, `Waiver_Expires_On__c`), resolution (`Resolution__c`, `Resolution_Reason__c`, `Resolved_By__c`, `Resolved_On__c`), and partner-safe messaging (`Partner_Message__c`, `Partner_Classification__c`).
- `Deal_Conflict_Analysis_Run__c` already implements Sprint 35 §35.27's analysis versioning (`Deal_Conflict_Analysis__c` in the spec) — `Active_Run_Key__c` (unique active-run key), `Input_Hash__c`, `Rule_Set_Version__c`, `Current__c`.
- `DealConflictCommandService.apply()` already implements Sprint 35 §35.32's exact command list almost verbatim: Assign Conflict, Start Investigation, Request Evidence, Submit Evidence, Confirm Conflict, Resolve Conflict, Waive Conflict, Mark False Positive, Escalate Conflict, Reanalyse Deal — including critical-severity waiver gating (`validateWaiver`, requiring extra authority for `Severity__c = 'Critical'`, matching §35.34's `PartnerSync_Waive_Critical_Deal_Conflict`).
- **Two permission sets already exist anticipating this exact workflow**: `PartnerSync_Critical_Conflict_Authority` (grants `PartnerSync_Waive_Critical_Conflict` + read on `Deal_Conflict__c`) and `PartnerSync_PDLM_Admin` (grants `DealConflictCommandController`). These match Sprint 35's permission design closely.
- **The actual gap: `DealConflictCommandController` has exactly one method — `executeCommand(String requestJson)` — no query/list endpoint, and zero LWC calls it.** The rich, already-built, already-permissioned investigation workflow (assign → investigate → request evidence → confirm/resolve/waive/escalate) has no way for a human to reach it. This is the same "engine built, no UI" pattern found in the broader gap review (§4 of [prm-gap-review-2026-09-25.md](prm-gap-review-2026-09-25.md)) — now confirmed for conflict investigation specifically.
- **What's genuinely missing, not just unreached**: only one conflict rule exists (`Deal_Conflict_Scoring_Rule__mdt`'s single `Existing_Registration` record), against Sprint 35 §35.15's 8 initial rules. Scoring is single-factor (one `Weight__c` per rule) rather than the additive multi-factor model in §35.23. `Deal_Validation_Result__c` doesn't exist as a name, though `Deal_Validation_Finding__c` already covers the same intent under a different name — not a gap, a naming difference to note, not fix.

### 2.2 Lead distribution (Sprint 22B) — still genuinely unbuilt

Unchanged from the first-pass review: `LeadDistributionService.assignLeadToPartner` is caller-driven manual assignment with no rule evaluation, `Lead_Distribution_Rule__mdt`'s 5 seed records are empty skeletons, and there's no `Partner_Lead_Assignment__c` aggregate at all — Sprint 22B's central architectural correction (assignment state as its own durable, re-assignable record rather than fields on `Lead`) doesn't exist yet in any form.

## 3. Phase 1 scope

Both pieces below follow patterns already proven twice in this codebase this session (the generalized `Approval_Plan__c`/`Approval__c` engine, and the `Deal_Review_Step*`/`psDealReviewStepWorkspace` build): a selector + domain + workspace-service + Aura controller + LWC, with an `assertAuthority()`-style gate, mirroring the object's existing command service rather than replacing it.

### 3.1 Conflict Workbench (Sprint 35 Phase 1) — done (2026-09-25)

Shipped the missing read/UI layer for the command layer that already existed — no new objects, no new command logic:

- New `DealConflictSelector` — `selectPendingConflicts()`/`selectConflictDetail(Id)`. Simpler than `DealReviewStepSelector`'s "my queue" split: `Deal_Conflict__c` authority is a single flat `PartnerSync_Resolve_Deal_Conflict` custom permission, not per-record assignment (`DealConflictCommandService.assertAuthority()` never checks `Assigned_To__c`), so every open finding is shown to every holder rather than filtering to "assigned to me."
- New `DealConflictWorkbenchService`/`DealConflictWorkbenchDomain` — gated by that same permission (there's no separate view-only access today), mapping to new `DealConflictWorkbenchListDTO`/`DealConflictWorkbenchDetailDTO`.
- Extended `DealConflictCommandController` with `getPendingConflicts()`/`getConflictDetail(Id)` alongside its existing `executeCommand`.
- New `psDealConflictWorkbench` LWC — queue + detail + action panel for all 10 already-built commands (Assign/Start Investigation/Request Evidence/Submit Evidence/Confirm/Resolve/Waive/Mark False Positive/Escalate/Reanalyse), mirroring `psDealReviewStepWorkspace`'s shape. Surfaces `Evidence_Summary__c`/`Reviewed_Evidence__c` and the waiver fields, previously populated but never displayed anywhere.
- New dedicated `Conflict_Workbench` Experience Cloud route/view (not added to the already-crowded `Deal_Review` page, which stacks three workspaces already) — wired into `psInternalDashboard`'s quick-action tiles so it doesn't repeat the orphaned-page pattern the gap review found repeatedly.
- Found and fixed two real, pre-existing permission gaps while wiring this up: `PartnerSync_PDLM_Admin` had `DealConflictCommandController` class access but neither the `PartnerSync_Resolve_Deal_Conflict`/`PartnerSync_Waive_Critical_Conflict` custom permissions nor `Deal_Conflict__c` object access — meaning an admin holding only that permission set could never actually pass `assertAuthority()`. `PartnerSync_Deal_Reviewer` held the custom permission but no `Deal_Conflict__c` object read grant. Both fixed.

**Deferred to a later phase, not Phase 1**: additional conflict rules beyond the existing one (§35.15's remaining 7), multi-factor weighted scoring (§35.23), `Deal_Conflict_SLA__mdt` (an ad-hoc `SLA_Due__c` field already exists; a real SLA/escalation engine is a separate, later piece of work), and any Data Cloud/external matching (§35.19 Stage 4 — the master doc itself scopes this as optional, for high-scale customers, not part of the base package).

### 3.2 Lead Distribution — Partner Lead Assignment (Sprint 22B Phase 1) — done (2026-09-25)

A trimmed slice of §22B.2-22B.16, keeping the core architectural correction (durable assignment aggregate + commands) and deferring the elaboration (scoring, capacity, business-hours SLA):

- New `Partner_Lead_Assignment__c` — `Lead__c`, `Partner_Account__c`, `Partner_Contact__c`, `Status__c` (trimmed at build time from the originally-planned 8-value set to the 3 values the shipped code actually produces or transitions to: `Assigned`/`Accepted`/`Rejected` — `Planned`/`Expired`/`Reassigned`/`Converted`/`Cancelled` deferred with their own lifecycle logic, not shipped as unused picklist entries), `Assignment_Strategy__c` (`Manual`/`Round Robin` only, same "only ship values actually used" discipline), `Distribution_Rule_Key__c`, `Routing_Reason__c`, `Assigned_On__c`, `Response_Due_On__c`, `Accepted_On__c`, `Rejected_On__c`, `Rejection_Reason__c`, `Active_Assignment_Key__c` (unique — same concurrency-safe pattern as every other `Current_Plan_Key__c` in this codebase), `Version_Number__c`. Deferred: capacity snapshot fields, SLA/escalation fields, reassignment lineage lookups (`Previous_Assignment__c`/`Reassigned_To__c`) — a rejected assignment creates a fresh record rather than a linked chain for now.
- Lead keeps its existing `Partner_Account__c`/`Lead_Distribution_Status__c` fields as **projections**, written by the assignment command handlers, per §22B.5 — no renaming, no new fields on Lead, preserving backward compatibility exactly as the master doc directs for `Deal_Registration__c` elsewhere.
- One real `LeadAssignmentStrategy` — Round Robin, via `RoundRobinAssignmentStrategy` (`SELECT Partner_Account__c, MAX(Assigned_On__c) ... GROUP BY Partner_Account__c` among eligible candidates: never-assigned partners win immediately, otherwise the least-recently-assigned partner does). §22B.9 lists Fixed/RoundRobin/CapacityBased/WeightedScore/Territory/AIRecommended; the master doc explicitly says AI must not be required for the core product, and Round Robin needs no criteria data to be useful, unlike the other four.
- `LeadDistributionService.distributeLead()` walks the active `Lead_Distribution_Rule__mdt` records in priority order and **skips** (does not hard-fail on) any rule whose `Distribution_Method__c` has no implemented strategy yet — necessary because all 5 seeded rules are active with Territory/Product/PartnerTier ranked above Round Robin, and only Round Robin has a handler today.
- Command-based Accept/Reject: new `LeadAssignmentCommand`/`LeadAssignmentCommandService`, mirroring `DealReviewCommandService`'s pattern (`FOR UPDATE` lock, `assertAuthority()` — the accepting/rejecting user must be a contact of the assigned `Partner_Account__c`, `expectedVersion` check, status-transition guard, releases `Active_Assignment_Key__c` on decision). `LeadDecisionService.processDecision()` was rewritten as a thin facade onto this command service — its original `LeadDecisionRequestDTO`-keyed-by-`leadId` signature is unchanged, so `psPartnerLeads.js` (its only caller) needed zero changes; its jest suite passes unmodified.
- `assignLeadToPartner()` (manual assignment) and `distributeLead()` (rule-driven) now share a `createAssignment()` helper so both origins produce the same durable `Partner_Lead_Assignment__c` record the command layer operates on.
- `Lead_Distribution_Log__c` keeps its existing role as the audit trail (§22B.5's own recommendation: "Lead_Distribution_Log\_\_c could then become a true event/audit log").
- Retained `Lead_Distribution_Rule__mdt` as-is; matching uses only the criteria fields that exist on this org's `Lead` (`Country`, `Industry` — there is no custom Region/Territory field on Lead in this org, unlike the master doc's implied criteria set, so Region-based matching is not possible here without a schema addition).
- `LeadDistributionController.distributeLead(Id)` added as the one new Aura entry point.
- Permission grants: `Partner_Lead_Assignment__c` added to `PartnerSync_Channel_Manager` (Create/Edit/Read) and `PartnerSync_Internal_Admin` (full CRUD), mirroring the existing `Lead_Distribution_Log__c` grant shape on both. Deliberately not granted to `PartnerSync_Partner_User`/`PartnerSync_Partner_Admin`, matching that same precedent.

**Known gap carried forward, not silently dropped**: `distributeLead()` has no dedicated UI entry point in this phase — like `assignLeadToPartner()` before it, it's reachable only via direct Apex/Aura call, not from any button on an internal page. Building a "Lead Ops" queue/page to trigger it is deferred, not forgotten.

**Deferred to a later phase, not Phase 1**: `PartnerEligibilityService`'s full criteria list (start with "partner active + program status," already validated by `LeadDistributionSelector.selectActivePartnerAccount`), `Lead_Distribution_Score__mdt` and weighted candidate scoring, capacity-based/territory/AI strategies, `Deal_Provenance` fields on `Deal_Registration__c` (`Origin_Type__c`/`Originating_Lead__c` from Sprint 34A §4 — real and worth doing, but a Deal-side change, out of scope for a Lead-side Phase 1), the full command-bus/idempotency-ledger infrastructure from Sprint 34A (Phase 1 reuses the existing `without sharing` + `assertAuthority()` pattern already proven for Approval/Deal Review, not a new platform-wide command bus), a dedicated internal UI entry point for `distributeLead()`.

## 4. Schema hygiene already shipped (2026-09-25)

Following the same methodology used on the `Approval_Plan__c`/`Approval__c`/`Approval_Condition__c` family (extract every literal value actually written in Apex, convert Text → non-restricted Picklist with exactly that value set):

| Field                                        | Values found                                                                                                              | Converted?                                                                                                                              |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `Deal_Conflict__c.Status__c`                 | Open, Assigned, Investigating, Evidence Requested, Confirmed, Escalated, Resolved, Waived, False Positive, Superseded     | ✅                                                                                                                                      |
| `Deal_Conflict__c.Severity__c`               | Critical, High                                                                                                            | ✅                                                                                                                                      |
| `Deal_Conflict__c.Subtype__c`                | Same Customer Account, Identity Fingerprint                                                                               | ✅                                                                                                                                      |
| `Deal_Conflict__c.Partner_Classification__c` | Overlapping Registration (only value written today)                                                                       | ✅ (single-value, non-restricted, so a future value needs no metadata deploy)                                                           |
| `Deal_Conflict__c.Type__c`                   | Sourced from `Deal_Conflict_Scoring_Rule__mdt.Conflict_Type__c`, itself a Text field an admin can set to anything         | **Left as Text** — converting would break the moment an admin configures a new conflict type via CMDT without a matching picklist value |
| `Deal_Conflict__c.Resolution__c`             | Free-text resolver-typed reason (`command.reason`), not an enum                                                           | **Left as Text** — genuinely freeform                                                                                                   |
| `Deal_Conflict_Analysis_Run__c.Status__c`    | Running, Completed, Superseded                                                                                            | ✅                                                                                                                                      |
| `Deal_Validation_Finding__c.Status__c`       | Current, Superseded                                                                                                       | ✅                                                                                                                                      |
| `Lead_Distribution_Log__c.Status__c`         | Pending, Assigned, Accepted, Rejected, Converted (mirrors `Lead.Lead_Distribution_Status__c`'s existing picklist exactly) | ✅                                                                                                                                      |

**Side finding, not fixed here:** `Lead_Distribution_Log__c.Assignment_Status__c` (already a picklist: Pending/Assigned/Accepted/Rejected/Reassigned/Failed) is never written by any Apex code — `Status__c` is what's actually populated. These two fields look redundant.

## 5. Open decisions

- **Conflict Workbench placement**: new dedicated page, or added to the existing `Deal_Review` page alongside `psDealReviewWorkspace`/`psApprovalWorkspace`/`psDealReviewStepWorkspace`? That page is already carrying three workspaces; a fourth may be better as its own page with its own nav entry.
- **Round Robin's actual criteria**: which `Lead_Distribution_Rule__mdt` fields does Round Robin need populated to be useful on day one — region/country only, or also lead type/industry? Affects how much of §22B.6's 22-field list Phase 1 actually needs.
- **Confirm target org edition** before any future phase considers Data Cloud/external matching (§35.19 Stage 4) — unchanged from the prior pass, still unconfirmed.
