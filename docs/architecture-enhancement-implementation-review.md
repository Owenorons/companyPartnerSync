# Architecture enhancement implementation review

Date: 2026-09-25

## Purpose and interpretation

The PartnerSync beta has been tested. That testing informed the enhancements recorded in [the architecture history](architecture-design-and-enhancement.md), particularly the deal framework. This review accepts that context and maps the latest architectural decisions to the current repository. It is an enhancement reconciliation, not a reassessment of whether the beta was tested.

The history remains intact. Earlier proposals explain previous designs; later corrections take precedence for the capability they address. Sprint numbers identify architectural workstreams, not proof that every described component is implemented or missing.

Evidence is from static inspection of the current working tree, not a fresh Salesforce test execution or comparison with the contents of an installed beta. Class and test presence establishes implementation evidence, not completion of every architectural acceptance criterion.

## Governing decisions

| Area          | Latest applicable direction                                                              | Implementation consequence                                                                          |
| ------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Deal identity | Retain `Deal_Registration__c` as the canonical root                                      | Extend the existing aggregate and compatibility facades; do not introduce a replacement `Deal__c`   |
| Lifecycle     | Registration, conflict, review, approval, protection and participants own separate state | Do not implement the opening proposal as one large registration status list                         |
| Approval      | Intermediate steps do not approve the registration; finalisation evaluates all gates     | Preserve `ApprovalFinalisationGuard` and registration finalisation orchestration                    |
| Protection    | First-class temporal protection is authoritative; root dates are projections             | Reconcile the target with the existing `Deal_Protection_Grant__c` before adding or renaming objects |
| Commands      | Shared execution guarantees across domain-owned handlers                                 | Extract common infrastructure incrementally without replacing working domain rules                  |
| Events        | Durable business records and delivery outbox are distinct from platform-event transport  | Connect existing persistence and consumers, then extend their guarantees                            |
| Lead handoff  | Standard Lead and assignment lifecycle precede independently governed PDLM               | Retain assignments and source links; introduce conversion policy and provenance incrementally       |
| Licensing     | Core / Growth / Enterprise plus add-ons; partner programme tiers are separate            | Continue the existing licensing implementation plan                                                 |
| AI            | Additive intelligence with bounded actions; deterministic workflows remain independent   | Reuse provider, governance and quota services while introducing the later policies                  |
| Packaging     | Enhance the existing `psync` managed package and subscriber setup model                  | Preserve public contracts and evaluate metadata changes against actual package state                |

### Concrete integration work

1. **Authorize command replays before returning stored results.** Registration execution looks up a completed result by command key before its user-mode record query and handler validation. Bind a replay to the aggregate and command identity, verify current access, and reject key reuse with a different payload. This is a static code finding requiring a targeted regression test; it is not evidence of an observed beta incident.
2. **Connect the outbox to transport.** `DealEventService` and conflict commands insert `Deal_Event_Outbox__c`. No production drain for that object was found. Existing `PlatformEventPublisherService`, `PartnerSyncEventHandler`, audit/notification/webhook consumers and `EventDLQService` are reusable infrastructure. The missing work is durable dispatch, publication confirmation, bounded retry and consistent consumer deduplication—not creation of an event system from scratch.
3. **Unify execution guarantees without collapsing aggregate ownership.** Registration/conflict use the deal ledger; protection records actions; reviews, approvals, participants and leads have their own execution patterns. Define shared authorization, request identity, version checks, transaction ownership and event envelopes, then adapt one domain at a time.
4. **Make conflict evaluation consume authoritative protection.** Candidate discovery currently reads `Deal_Registration__c.Protection_End_Date__c`; its status filter includes Submitted, Under Review and Approved but not Approved with Conditions. Reconcile eligibility with active grants, scope and temporal policy. Add explicit conditional-approval and suspended/expired grant cases before changing matching behavior.
5. **Make deferred orchestration observable.** Registration finalisation catches protection-command exceptions and logs deferred activation; originating participant creation also has a logged fallback. Define which outcomes are legitimate pending conditions and which require a retryable operational work item. Avoid silent indefinite incompleteness.
6. **Define bulk execution per command family.** Registration execution is currently a single-command API with multiple queries/DML statements. Do not interpret the document's 200-record criterion as permission to loop that API 200 times in one transaction. Establish bulk interfaces or bounded asynchronous execution and test the intended transaction shape.

Licensing provisioning and enforcement can progress alongside deal enhancements under its existing plan. The trusted subscription source/add-on contract is a real product integration dependency: do not invent a licensing backend or treat subscriber-editable configuration as proof of purchase.

## Verification for each enhancement

Use existing Apex and LWC suites as the starting point, adding tests for changed business behavior rather than duplicating implementation assertions. In particular:

- Exercise internal reviewer, originating partner, invited partner and unrelated partner scenarios for each affected boundary.
- Verify command retries, stale versions, rollback, duplicate events and concurrent reservations where applicable.
- Test bulk behavior using the actual intended transaction/chunk size.
- Re-run affected deal, approval, MDF, lead and onboarding paths when shared services change.
- Verify the enhanced package in subscriber context, including permissions and the relevant Experience Cloud actions. Record candidate-specific evidence without recasting the previously tested beta as untested.

## Review outcome

The main deal framework is already present. The next development phase should strengthen and connect its command, event, conflict, review, approval, protection and participant implementations. Later post-sale capabilities build on those foundations. The architecture history provides the design evolution; this companion supplies a current implementation map without rewriting that history.
